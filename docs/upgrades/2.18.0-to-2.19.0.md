# Upgrade NKP from 2.18.x to 2.19.0

This procedure upgrades the NKP platform and then moves the management cluster
and workload clusters to Kubernetes 1.36.2 with the Rocky Linux 9.8 node image.

!!! note "Upgrade through 2.18 first"
    NKP 2.17.x clusters cannot upgrade directly to 2.19.0. Follow
    the 2.18 version of this documentation, then return here. Use the version
    selector in the header to switch versions.

## Critical prerequisites

### Infrastructure versions

NKP 2.19.0 supports Prism Central `pc.7.5` and `pc.7.6`, and AOS 7.5 and 7.6.
Upgrade Prism Central and AOS before NKP if you are on an older version.

!!! warning "Ubuntu vGPU"
    The NKP 2.19 support matrix no longer lists vGPU for Ubuntu 22.04 and
    24.04, and NKP 2.18 did. If you use vGPU on Ubuntu, confirm support before
    you upgrade.

### Prism Central Projects 2.0

A Nutanix cluster must use **one** Prism Central project for all its resources,
including the control plane, every worker pool, and volume groups. If a 2.18
cluster spans projects, for example a control plane in the default project and
GPU pools in a user-defined project, move all nodes into one project **before**
the upgrade.

NKP 2.19 introduces the unified `--pc-project=<project-name>` flag. Omit it for
the default project, which resolves to `_internal`. The older
`--control-plane-pc-project` and `--worker-pc-project` flags are deprecated, so
update any scripts that use them. A user-defined project requires Prism Central,
Prism Element, and AOS 7.6 or later.

!!! warning "Plan this early"
    Changing a cluster's project after creation is not supported. A cluster that
    must move into a user-defined project might need Nutanix Support to migrate
    existing volume groups. Do not leave this for the maintenance window.

### Registry credentials

Management clusters without a Nutanix Docker Hub registry token must provide one
during the upgrade. A regular Docker Hub account does not grant access to the
Nutanix repository. `nkp upgrade kommander` checks for the token at the start and
stops if it is missing.

### Catalogs and automation

- Migrate remaining `AppDeployment` resources from `GitRepository` catalogs to
  `OCIRepository` catalogs. `GitRepository` catalogs are no longer supported.
- Remove `--kommander-applications-repository` from scripts and pipelines. It is
  no longer supported by `nkp install kommander` and `nkp upgrade kommander`.
- `nkp upgrade workspace` is deprecated. Use the cluster and platform
  application upgrade steps below.

### Known limitation: single-instance Nutanix Enterprise AI

A single-instance Nutanix Enterprise AI deployment can block worker nodes from
draining during a cluster upgrade. Check the 2.19 release notes for the
documented adjustment before you start.

### Fleet health

Every management and workload cluster must be on NKP 2.18 and healthy. Verify
backups, spare capacity for rolling replacement, disruption budgets, and
Cluster API health. All platform applications on a workload cluster must be
healthy before you upgrade it.

```bash
export MANAGEMENT_KUBECONFIG="$HOME/nkp-mgmt-cluster.conf"
export KUBECONFIG="${MANAGEMENT_KUBECONFIG}"

kubectl get nodes
kubectl get clusters -A
kubectl get pods -A
kubectl get helmreleases -A --no-headers | grep -v "True" || echo "ALL APPS READY"
```

## Required upgrade sequence

1. Upgrade Kommander on the management cluster.
2. Upgrade the management cluster Kubernetes version and node image.
3. Upgrade each workload cluster, from the UI or with the CLI.

Never upgrade a workload cluster before its management cluster.

## Prepare the artifacts

Install the NKP 2.19 CLI. Keep the 2.18 binary while the fleet contains both
releases.

```bash
tar -xvzf nkp-bundle_v2.19.0_linux_amd64.tar.gz
sudo install -m 0755 ./nkp-v2.19.0/cli/nkp /usr/local/bin/nkp
nkp version
```

Upload the NKP 2.19 node image to Prism Central. Download it from the Nutanix
Support Portal under **NKP Operating System Images**, verify the published
checksum, and do not rename it. For air-gapped environments or custom images, see
[Node images](../node-images/index.md).

```bash
export TARGET_VM_IMAGE=nkp-rocky-9.8-release-cis-1.36.2.qcow2
```

The filename is an example. Use the exact name in Prism Central.

## Upgrade Kommander

```bash
nkp upgrade kommander --kubeconfig "${MANAGEMENT_KUBECONFIG}"
kubectl get helmreleases -A --no-headers | grep -v "True" || echo "ALL APPS READY"
```

The command runs checks first, then upgrades the management plane and platform
applications. It can show no output for several minutes. To follow progress, watch
the HelmReleases from a second terminal.

!!! tip "Field note: expect to log in again"
    After the Kommander upgrade the authentication token changes and the UI returns
    to the login screen. Token-based kubeconfigs stop working, but a
    certificate-based administrator kubeconfig keeps working.

## Upgrade the clusters

After `nkp upgrade kommander`, you can upgrade each cluster from the NKP UI. No
further CLI commands are needed. The CLI still works and follows the same
structure as the 2.18 upgrade. Choose one method per cluster and do not mix them.

Upgrade the management cluster first, then the workload clusters. For
ClusterClass clusters, the workflow upgrades platform applications first, then
Kubernetes and the cluster infrastructure.

### Option 1: NKP UI

1. Open **Administration → Upgrades**.
2. Choose the cluster and select NKP 2.19.0.
3. Select the new node image for the control plane and each node pool.
4. Start the upgrade and follow it in the upgrade tracker.

The pre-checks always run from the UI. Upgrade clusters in controlled batches and
verify each one before starting the next.

### Option 2: NKP CLI

Discover the cluster name and namespace instead of guessing them:

```bash
kubectl get clusters -A

export CLUSTER_NAME=nkp-mgmt-cluster
export CLUSTER_NAMESPACE=kommander
```

```bash
nkp upgrade cluster nutanix \
  --cluster-name "${CLUSTER_NAME}" \
  --namespace "${CLUSTER_NAMESPACE}" \
  --vm-image "${TARGET_VM_IMAGE}" \
  --kubeconfig "${MANAGEMENT_KUBECONFIG}"
```

Run it for the management cluster first and wait until it is healthy. Then repeat
it for each workload cluster, using that cluster's name and namespace, which is
usually its workspace.

For clusters that are not ClusterClass-based, upgrade platform applications with
`nkp upgrade platform-apps`, then follow the cluster-specific procedure.

When Flux owns the cluster definition, update the declared Kubernetes version and
node image in Git instead. Do not combine imperative and GitOps ownership.

Cluster API replaces the nodes one by one. Wait until all nodes are `Ready` on
Kubernetes 1.36.2 and all applications are healthy before moving on.

!!! tip "Field note: a yellow warning is not a failure"
    Early in the Kubernetes step, the upgrade tracker can warn that a
    `BeforeClusterUpgrade` hook timed out. Cluster API retries on its own. Wait a
    few minutes before changing anything.

## Replace Kubernetes Dashboard

NKP 2.19 replaces Kubernetes Dashboard with Headlamp. An upgraded cluster keeps
the existing Dashboard running and leaves Headlamp disabled until you enable it.
Nutanix recommends migrating to Headlamp as soon as possible.

## Monitor and verify

```bash
kubectl get clusters,machines -A
kubectl get kubeadmcontrolplanes,machinedeployments -A

kubectl --kubeconfig "${MANAGEMENT_KUBECONFIG}" get nodes
kubectl --kubeconfig "${MANAGEMENT_KUBECONFIG}" get pods -A
kubectl --kubeconfig "$HOME/${WORKLOAD_CLUSTER_NAME}.conf" get nodes
kubectl --kubeconfig "$HOME/${WORKLOAD_CLUSTER_NAME}.conf" get pods -A
```

Confirm Cluster API readiness, application health, storage, external endpoints,
monitoring, and backups. Remove the old Rocky Linux 9.7 node image from Prism
Central only after no virtual machine uses it.
